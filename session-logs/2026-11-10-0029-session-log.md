## SDK Rendering Reuse Assessment

The owner's question is not an all-or-nothing choice between reimplementing
everything and recreating seven SDK views. Public SDK responsibilities differ:

1. [Renderer](https://developers.arcgis.com/javascript/latest/references/core/renderers/Renderer/)
   objects describe how features receive symbols; they are not standalone
   GPU drawing engines. Importing renderer definitions is distinct from
   creating a MapView and its rendering context.
2. [symbolUtils](https://developers.arcgis.com/javascript/latest/references/core/symbols/support/symbolUtils/)
   provides displayed-symbol evaluation and small symbol previews. A bounded
   probe could test the actual city CIM symbols as cached marker images for
   the existing canvas. Preview-to-texture conversion, anchor/size/rotation,
   attribute/scale variation, fidelity, dependencies and context allocation
   must be measured; this integration has not been implemented or certified.
3. [BaseLayerViewGL2D](https://developers.arcgis.com/javascript/latest/references/core/views/2d/layers/BaseLayerViewGL2D/)
   lets custom code share a MapView's context and offers tessellation helpers.
   It is a MapView-owned layer view, not a supported adapter that runs the
   SDK's complete layer renderer in an arbitrary user-owned context. The
   developer still supplies shaders, meshes, textures and GL state.

The installed 4.32 sources corroborate these boundaries: symbolUtils exposes
preview/evaluation helpers, and BaseLayerViewGL2D obtains its context from
`this.view.stage.context.gl`. Its polygon path imports earcut, so switching to
that helper alone must not be assumed to repair topology or projection issues.
The current online docs describe a newer SDK; no upgrade was performed.

No documented drop-in API for complete SDK layer rendering into this custom
multi-projection canvas was identified. Removing WebMap loading/UI overhead is
separate from reducing independently rendered views. Shared-context custom
layers do not automatically provide seven native independently projected
MapView renderings. Private engine extraction is not proposed as a supported
solution.

Recommended next investigation: test public symbol helpers against the actual
CIM city symbols without constructing MapViews, measuring both pixels and
created/live contexts. Separately reproduce and resolve polygon/outline defects
against independent native references and rerun the full area audit. Symbol
previews cannot repair polygon geometry or supply the missing imagery stack.
This is a research recommendation, not an implemented rendering fix.

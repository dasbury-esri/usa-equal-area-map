## Implemented Changes

1. `coverage.js` samples each selected pane's inverse projection on a 17x17 grid,
   with a margin of 25% of its width/height on each side and a two-degree guard.
   Geographic bounds are split at the dateline; overlapping rectangles are merged.
   Invalid inverse samples conservatively fall back to world coverage.
   One multipart WGS84 intersects filter is shared by counts, IDs and geometry
   pages. This selects features, not clipped fragments: intersecting countries
   can still return large polygons extending well outside the requested areas.
2. Service generalization is half a CSS pixel at the requested scale, converted
   using 111,320 meters per degree. At 1:24,000,000 this is 3,175m, or about
   0.02852138 degrees, instead of fixed 0.001 degrees. It is an approximate
   geographic tolerance, not a certified half-pixel error under every projection.
   A 150ms navigation debounce refines after a square-root-of-two zoom-in or
   leaving cached coverage. Refinement requests only buffered current pane areas.
   A complete current result replaces prior geometry; stale/incomplete results
   do not replace it. Pan, recenter, resize and zoom all participate.
3. Equivalent fill, outline and marker symbols are batched across features,
   retaining layer order. The fixture has five symbol batches, hence twenty
   draws over four panes before culling. Fills and outline symbols use distinct
   primitives and remain separate batches.
4. Each batch is partitioned into five-degree geographic cells, capped at
   4,096 instances per chunk. Bounding boxes include all actual vertices.
   Transform feedback applies the existing GPU projection at upload time to
   produce exact projected-vertex bounds per pane. Invalid bounds fail open;
   screen-space symbol padding is included. Offscreen chunks are skipped.
   Adjacent visible ranges are coalesced, then GPU-copied into a shared scratch
   buffer so each visible symbol still uses one draw per layer per pane.
   Geometry is not downloaded or CPU-uploaded again during ordinary panning.
5. The comparison supports `COMPARISON_BASE`, `--no-four`, pan transfer accounting,
   and a test-only runtime main-app fixture for the production build, whose
   pre-startup fixture hook is intentionally dev-only.

Profiling exposed a large preparation cost in Terraformer's ring-containment
checks. A separately measured bounding-box prefilter partitions disjoint ring
components before calling the same converter. It reduced preparation by about
eleven seconds but did not resolve startup performance. It does not implement
new polygon repair or change the projection/stroke shader algorithms.

The main application has seven live views versus four prototype panes; layouts
and workloads are not identical. Production-main setup opens the ordinary app,
then replaces each live map's layers with clones of the same three selected
items and applies the same simple symbols before settling. Its initial bytes
and time include ordinary startup and that replacement, so they are not a clean
three-layer-only startup comparison. No production entry code was changed to
expose a testing hook. Removed fixture layers are destroyed.

**Startup remains a major regression, not a solved performance problem.**
Final production preparation took 68,307.7ms cold and 67,800.3ms warm; downloads
took 15,057.2ms and 1,490.8ms. Before the ring prefilter, preparation was about
78 seconds. CPU sampling attributed roughly 73 seconds in a profiled run to
Terraformer edge-intersection and containment work, and about 4.8 seconds to
projected chunk bounds. The prefilter improved only part of that workload.
Area refinement also rebuilds meshes and can incur that cost. There is no
overall load-time speedup claim, and the prototype remains unaccepted.
